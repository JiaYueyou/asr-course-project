**【看稿找代码】** `asr-my-project/prepare_timit.py` **第 27–32 行**：

**【看稿找代码】** 同文件 **第 43–44 行**（`frames_of`）：

### 2:20–3:40 文本清洗、清单与词表

> 文本清洗只有三步，写在 `prepare_timit.py` **第 35–40 行**。

**【看稿找代码】** `prepare_timit.py` **第 35–40 行**（`clean_text`）：
> “先 NFKC 规范化，再转小写，最后用正则 `[a-z']+` 只保留小写字母和词内撇号，空格分词。这样训练文本和评估参考文本来自同一份清单，不会出现‘训练带标点、评估去标点’的不一致。”

> 清单格式是**空格分隔**：第一段是文件名，后面全部是文本。写清单在 **第 116–123 行**。

**【看稿找代码】** `prepare_timit.py` **第 116–123 行**：
> “这里有三件事：读 wav、断言 16 kHz 单声道、写 PCM16；最后一行 `f.write(f"{utt}.wav {text}\n")` 就是清单格式。下游 `dataset.py` 用 `split(maxsplit=1)` 解析，正好对上。”

**【展示证据】** 打开 `data/proc/transcription.txt`，指前 3 行：
```text
FCJF0_SA1.wav she had your dark suit in greasy wash water all year
FCJF0_SA2.wav don't ask me to carry an oily rag like that
FCJF0_SI1027.wav even then if she took one step forward he could catch her
```
> “第一条带 `don't`，说明撇号被保留；三行都是小写；文本内部有空格但文件名没有空格，所以 `split(maxsplit=1)` 不会切错。”

> 词表在 `prepare_timit.py` **第 125–148 行**生成。

**【看稿找代码】** `prepare_timit.py` **第 125–132 行**：
> “只从本批语料实际出现的字符统计，不注入任何常见字。`blank` 固定索引 0，其余字符排序后编号，最终 29 类：blank、空格、撇号、a–z。没有 `<unk>`，因为 4618 条语料的字符集合是封闭的；真出现集外字符，`encode` 会直接报错，而不是悄悄映射到 UNK 污染 loss。”

### 3:40–5:20 特征提取与缓存

> 音频进来以后，第一步是 log-mel。入口在 `dataset.py` **第 20–51 行**，实现在 **第 54–77 行**，mel 滤波器组在 **第 80–99 行**。

**【看稿找代码】** `dataset.py` **第 20–51 行**（`extract_mel_spectrogram`）：
> “参数是 16 kHz、80 mel、512 点 FFT、400 点窗、160 点帧移。输出 `[T, 80]`，每秒 100 帧。”

**【看稿找代码】** `dataset.py` **第 54–77 行**（`_simple_mel`）：
> “关键点：这里**没有用 librosa**，而是 NumPy 向量化。原因写在上面 **第 33–36 行**的注释里——本环境 librosa 首次调用有 numba JIT，多进程预计算时每个 worker 都要编译一次，取数会从毫秒级退化成分钟级。现在约 2 ms/条。”

**【看稿找代码】** `dataset.py` **第 80–99 行**（`_create_mel_filterbank`）：
> “三角滤波器组用 2595·log10(1+f/700) 的 mel 刻度生成，低频从 80 Hz 起，高频到奈奎斯特频率（8 kHz）。注意 `f_min/f_max` 这两个参数在函数签名里保留了，但当前滤波器组实现没有使用它们，实际带宽是 80 Hz–8 kHz。最后 **第 76 行**做 `log10(max(x, 1e-10))`，把约 60 dB 的动态范围压下来。”

> 特征算一次就够了，所以我做了磁盘缓存，逻辑在 **第 148–189 行**、**第 435–490 行**、**第 492–519 行**。

**【看稿找代码】** `dataset.py` **第 148 行**、**第 334–343 行**：
> “缓存目录名是 `mel_<签名哈希>`，签名包含采样率、n_mels、n_fft、hop、win、提取后端和版本。改了任何一个特征参数，签名变化，自动换目录，不会误读旧特征。”

**【看稿找代码】** `dataset.py` **第 435–490 行**（`precompute_features`）：
> “训练开始前一次性把所有特征算完落盘；之后每个 epoch 只做 `np.load`。任务数超过 64 且进程数大于 1 时走多进程，否则串行；只补缺失或比源音频旧的条目。”

**【展示证据】** 打开 `data/proc/cache/mel_25da37945f/meta.json`：
```json
{"version":1,
 "signature":{"sample_rate":16000,"n_mels":80,"n_fft":512,
              "hop_length":160,"win_length":400,"backend":"numpy","version":1},
 "manifest_fingerprint":"8bb9ca59d1","num_files":4618,"elapsed_sec":0.06}
```
> “`num_files=4618`，签名就是刚才那组参数；这个目录实际有 4619 个文件（4618 条特征 + 1 个 meta），合计约 451.8 MB。”

> 性能上：全量预计算 28 秒（8 进程），之后全量遍历一遍 5.86 秒，平均 1.27 ms/条；数据集构造 0.079 秒；缓存命中检查 0.058 秒。这些数字在 `使用方式.txt` **第 154–159 行**有实测记录。

### 5:20–6:20 全局 CMVN 与变长组批

> 这一步是我认为**最容易出错、也最值得讲**的一步：归一化。

**【看稿找代码】** `dataset.py` **第 195–212 行**（`normalize_features`）：
> “标准化公式就是 `(x - mean) / std`。关键在于 mean/std 从哪来。”

**【看稿找代码】** `dataset.py` **第 521–557 行**（`compute_global_stats`）：
> “我统计的是**训练集全量**，不是每句话各自统计。本数据是 1,409,882 帧 × 80 维，得到一组全局 mean/std，存成 `cmvn_*.npz`，同时随 checkpoint 保存为 `feature_stats`。训练、验证、推理三边都用这一组。”

> 为什么不能逐条统计？短句统计不稳定；更重要的是，如果训练用全局、推理用逐条，输入分布就变了。原教学代码就有这个问题：训练 loss 正常，推理解码全空。我这里是**从设计上消除**，不是靠口头约定。

**【看稿找代码】** `dataset.py` **第 562–588 行**（`__getitem__`）：
> “取特征 → 超过 20 秒截断 → 用全局 stats 归一化 → 文本编码 → 返回 dict。注意 **第 574 行**，归一化就发生在这里。”

> 最后是变长组批，在 **第 591–622 行**。

**【看稿找代码】** `dataset.py` **第 591–622 行**（`collate_fn`）：
> “一个 batch 里句子长短不一，所以 padding 到 batch 内最大 T，同时把真实长度 `input_lengths`、`label_lengths` 一起返回。模型用 `pack_padded_sequence` 跳过 padding 帧，CTC 用真实长度算 loss。”

## 五、预判提问与回答

| 可能被问 | 建议回答 |
|---|---|
| 为什么只选 4618 条，不用 TIMIT 全量 6300？ | 1–8 秒、10–200 字符、`T >= 2L+1` 三条硬规则筛掉了不合规句子；SA1/SA2 默认保留，保证说话人覆盖。4618 条已是过滤后的可用全量。 |
| 为什么不用 librosa？ | 本环境 librosa 0.11 首次调用 numba JIT 分钟级，多进程每个 worker 重复编译；NumPy 向量化约 2 ms/条，且训练/缓存/推理三处同一实现，避免特征漂移。见 `dataset.py` 第 33–36 行。 |
| 为什么词表没有 `<unk>`？ | 4618 条语料的字符集合是封闭的；UNK 在 CTC 里没有合理对齐语义，还会污染 loss。真出现集外字符应报错并回到数据阶段处理。 |
| 缓存会不会读到旧特征？ | 不会。目录名由“特征参数 + 后端 + 版本”的 md5 生成，参数一变自动换目录；单条音频重生成时 mtime 变化，只重算该条。 |
| 为什么归一化要用全局统计，而不是逐条？ | 逐条统计短句不稳定；更关键的是训练和推理必须同分布。全局 mean/std 存 checkpoint，推理端只读不重算。 |
| 测试集 1680 条从哪来？ | TIMIT 官方 TEST 划分；`data/proc_test` 单独生成，不参与训练。 |
| 数据处理最容易被忽略的风险是什么？ | 文本与清单不一致、训练/推理归一化不一致、`T < 2L+1`。前两个靠“单一数据源 + checkpoint 存统计量”消除，第三个在数据阶段硬过滤。 |
