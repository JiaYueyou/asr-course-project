## 二、口播稿

**0:00–0:15 开场**

> 我负责数据处理。一句话：把 TIMIT 的原始素材，变成后面训练和推理能直接读取的标准数据。产出是音频、清单、词表和一份特征缓存，都在 `data/` 目录下。

【看稿找代码】目录结构见 `README.md` 项目结构一节。

**0:15–0:45 第一段：原料入库**

> 第一步是 `prepare_timit.py`。它从原始 TIMIT 里按规则挑句子，统一采样率，把音频重新写成标准 wav，同时写一份「文件名 + 对应文字」的清单；最后统计出现过的字符，生成 29 类的词表，其中 0 号是 CTC 用的空白符，其余是空格、撇号和 26 个字母。

【看稿找代码】
- 写 wav 与 `transcription.txt`：`prepare_timit.py` 第 116–123 行
- 生成 `vocab.json`：`prepare_timit.py` 第 125–148 行

> 这一步之后，数据从「一堆散乱文件」变成了「音频 + 文本一一对应」的可遍历结构。

**0:45–1:25 第二段：特征化与缓存**

> 第二步在 `dataset.py`。每条音频进来，先做短时傅里叶那套前端，转成 80 维的 log-mel 特征；再做一次全局幅值归一化，让所有样本的数值范围一致；然后把整句文字查词表编码成数字序列。特征算一次就存成 `.npy` 文件，后面训练直接读缓存，不再重复算。这里的关键是**训练、推理、评测三处必须用同一套特征参数和同一份归一化统计量**，否则输入分布不一致，模型会莫名其妙变差。

【看稿找代码】
- 提 log-mel 特征：`dataset.py` 第 20–51 行
- 单条样本完整加工（特征 + 归一化 + 文本编码）：`dataset.py` 第 562–588 行
- 特征落盘缓存：`dataset.py` 第 435–490 行
- 全局归一化统计量：`dataset.py` 第 521–557 行
- 拼接变长 batch：`dataset.py` 第 591–622 行

**1:25–1:45 第三段：交给下游的约定**

> 我这一环对外承诺四件事：清单格式统一、词表固定 29 类、特征维度固定 80、归一化统计量随 checkpoint 一起保存。下游只要按这四个约定读，就不会出错。

**1:45–2:00 摆证据**

> 现在项目里的证据：`data/proc/audio` 有 4618 个 wav、`transcription.txt` 4618 行；`data/proc_test/audio` 有 1680 个 wav，覆盖 168 个说话人；`data/proc/cache/mel_25da37945f/` 是 451.8 MB 的特征缓存，4618 个 `.npy` 加一个 `meta.json`；`vocab.json` 里 `idx2char` 正好 29 项。

## 四、可能被问到的两句

- 为什么要缓存：避免每个 epoch 重算特征，训练时间主要花在 GPU 前向反向，而不是 CPU 上重复做频谱。
- 为什么词表里要有空格：参考文本本身带词间空格，识别结果也要带空格才能和标注逐字对比，否则 CER 会被空格差异污染。
